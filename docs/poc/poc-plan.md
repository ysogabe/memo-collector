# PoC 計画: ローカルモデルで Context Capture は成立するか

- 対象: [PRD](../prd/PRD.md) の「キャプチャ経路」と「後段トリアージ」
- 実施日: 2026-10-08
- 実施環境: MacBook (Apple M3 / 24GB) / macOS 27 / Python 3.12 / torch 2.14 (MPS) / transformers 5.19
- 結果: [poc-report.md](./poc-report.md)

## 1. 問い

元会話の設計原則は「キャプチャ時は重い処理をしない。解釈は後段」。その上で、ローカルの小型モデルが次を担えるかを確かめる。

| # | 問い | 主に検証するモデル |
|---|---|---|
| Q1 | 日本語の音声メモを、ホットキー解放から 2 秒以内に保存可能な状態にできるか | Whisper large-v3-turbo（MLX） |
| Q2 | 注釈の「意図」（todo / research / code / note / schedule）をローカルで推定できるか。音声のまま判定できるか | d1-omni-600M, d1-3B |
| Q3 | スクショから画面の種類と、**秘密情報の写り込み**を判定できるか（外部エージェントへ渡す前のガード） | d1-3B, d1-omni-600M, Apple Vision OCR |
| Q4 | 溜まったキャプチャを日本語で探せるか（テキスト・スクショ・音声） | EmbeddingGemma 2 |
| Q5 | 常駐アプリとして全部載せたときのメモリ・ロード時間は現実的か | 全部 |

## 2. 合格基準

上 3 行（所要時間・意図分類・秘密情報）は実験を始める前に決めた。下 2 行（検索・常駐メモリ）は exp02 / exp04 の結果が出た後に追加した基準なので、事前登録ではない点に注意。

| 項目 | 基準 | 根拠 |
|---|---|---|
| キャプチャ経路の所要時間 | p90 ≤ 2.0 秒（ホットキー解放 → 保存可能） | 会話の UI 案「1〜2 秒だけトーストを出して消える」 |
| 意図分類の精度 | ≥ 80%（未見データで） | 8 割外すと「後で直す」手間が入力の手間を上回る |
| 秘密情報検知の再現率 | ≥ 90%、誤検知率 ≤ 20% | 見逃しは外部送信事故に直結。誤検知は確認ダイアログで吸収できる |
| 検索 Recall@3 | ≥ 0.8 | Inbox を開いて上位 3 件以内に出れば実用 |
| 常駐メモリ | ≤ 4GB を目標、8GB を上限 | 16GB 機でも他アプリと共存させるため |

## 3. 方法

- **データ**: 画面モック 14 枚（GitHub / Zoom / Teams / VS Code / .env / ターミナル / PDF / Slack / Notion / Amazon / AWS IAM / 1Password / カレンダー）。うち 4 枚に**ダミーの**秘密情報。注釈 30 件（日本語・5 意図）、音声は macOS `say` の日本語 4 話者で合成（16kHz mono）。検索クエリはテキスト 10 件・画像 10 件。
- **ホールドアウト**: ルールベース分類器を作った後に、未見の注釈 22 件を別途作成して比較する（過適合の確認）。
- **計測**: すべてウォームアップ後の 1 件ずつの呼び出し。MPS は `torch.mps.synchronize()` で同期して計る。実験は 1 本ずつ順番に実行。
- **比較対象（ベースライン）**: 日本語キーワードのルール、埋め込みのゼロショット / kNN、Apple Vision OCR + 正規表現。

## 4. スコープ外

- Swift 実装（ScreenCaptureKit・AVAudioEngine・FluidAudio）での計測。PoC は Python で「モデルが役割を果たせるか」に絞る。
- 実発話・雑音環境・実画面での評価（次フェーズ。§5 参照）。
- FluidAudio / Parakeet JA（Core ML / ANE）との STT 比較。

## 5. 次フェーズで必要な追加検証

1. 実際の自分の声で 100 件程度を録り、STT と意図分類を再評価する。
2. Swift + ScreenCaptureKit でウインドウ単体スクショを撮り、実画面で OCR ガードを評価する。
3. FluidAudio（ANE）と Whisper（GPU）の比較。常駐中の消費電力も見る。
