# MVP の実機受け入れ（2026-10-15、Issue #1）

対象は M3 / 24GB、AC の実 Mac。M4 / 32GB は使用しない。アプリは Apple Development 署名の Release `00e95ef`。現 main `261d608` と `app/`・`Packages/` のソース差分がないことと、署名を確認した。個人 DB と分けた試験データだけを使用し、実音声・スクリーンショット・注釈・URL・個人 DB を Git へ入れない。

## 事前確認

- 実プロセスに試験用 `CC_DATA_DIR` と準備済みモデルルートが渡っていることを確認。ホットキーは Carbon で登録成功。Whisper の読み込みと warm-up、埋め込みと検索索引の準備が完了した。
- ユーザーが Safari の公開 LP で、実ホットキー・マイクを使って録音。HUD、保存通知、注釈、スクショ、URL の5項目を確認済み。
- DB を readonly で照合し、Safari の2件に注釈・音声・スクショ・公開 LP の URL が保存されていることを確認。最新の1件は押下→録音開始47ms、解放→保存1449ms、録音3.4秒。
- 事前操作の保存3件は測定開始前に全件を固定して除外した。これには6.2秒と15.2秒の長い録音（保存5585ms / 7535ms）と、ビルド中の試行を含む。無音で保存しなかった操作も別に保持する。速い1件だけを全体の性能判定には使わない。

## 実マイク20件の性能

ユーザーが2件を1組として10組、計20件を録音した。1件目の保存通知後約1秒で2件目を録音し、2件目の保存通知後3秒程度待つ手順。測定の開始時刻と事前確認の除外IDを先に固定し、今回のビルド・モデル検証・MCPクライアントを測定中は実行していない。録音の長さは実測2.2〜3.2秒。ユーザーは20件完了と通知・操作の異常なしを確認した。

| 指標 | n | P50 | P90 | 最大 | 判定 |
|---|---:|---:|---:|---:|---|
| 押下→録音開始 | 20 | 62ms | 81ms | 141ms | 全件150ms以下 |
| 解放→保存 | 20 | 1435ms | 1525ms | 2757ms | P90 2000ms以下 |
| 保存・音声・スクショ・URL・注釈・推論結果 | 20 | — | — | — | 全件あり、保存失敗0（自動ラベル採用とは別） |

全20件がSafariからの記録で、URL・スクショ・音声を保持し、ガードはclear。 **自動意図ラベルは20件すべて未分類だった。** 推論は実行され、19件はtodo 0.6068、1件はnote 0.5749が最大だったが、測定時のしきい値0.7で棄却された。「推論結果が保存された」ことを「自動分類できた」ことへ読み替えない。ユーザーの指摘を受け、当時の分類品質を合格とした報告を訂正した。今回の20件は文字起こしが2種類しかなく、20件の独立した意図評価データには数えない。事前確認を含む23件すべてが最新世代の索引へ入り、generation jobは全件succeededになった。手順に示したLPの単一URLとの完全一致は性能の判定条件にしていない。録音した内容・URL・画像を公開証拠には含めない。

最も遅い1件を除かず集計した。保存2757msのうちSTTは2722ms（Whisper pipeline2721ms）、encoder2457ms、decoder247ms、wait0ms、温度fallback0回。STTのエンコーダ部分が長いことは分かるが、熱・OS共有資源・外部負荷のどれが原因かは断定しない。全件2秒以下を保証する結果ではない。[全20件の匿名化数値](../e2e/results/20261015-mvp-live-acceptance/capture-metrics.json)。

ログの `pressToRecording` はOS押下→録音開始完了、`releaseToSaved` はOS解放→保存して `.saved` イベントを流す直前。後者を通知のピクセルが画面に描かれた時刻へ読み替えない。実通知の表示はユーザーの目視で別途確認する。P90は既存メニューと同じ最近傍順位法を使う。遅い値や失敗も残す。

## 未分類20件の原因と質問文の追加比較

今回の入力は、性能試験として繰り返した短い読む意思のメモ2表記。20件の独立した分類正解データではない。19件はtodo 60.68%、1件はnote 57.49%が最大となり、測定時の採用基準70%を全件下回った。しきい値を50%に落とすだけでは、著作した再現2表記のうち1件をnoteと誤分類する。処理完了のログをラベル付与の成功として報告した点を訂正する。[匿名化した出力分布](../e2e/results/20261015-mvp-live-acceptance/intent-diagnostics.json)。

既存の日本語質問文v1は再現2表記をどちらもtodoとして採用できた。一方、既存30件では分類24→25・正解21→24と改善しても、別の既存22件では分類13→14・正解13→13で、採用されたラベルの正解率が100%→92.9%へ低下した。codeの正しく採用された件数も5→1へ減るため、そのまま製品へ置き換えない。

元の5つの英語説明を残す補足候補も開発30件と再現2表記で比較した。英語で行動の説明を補うv2は再現2/2、開発30件の分類26・正解23。候補を固定して別の22件で確認すると分類13・正解13を維持したが、codeの採用は5→3へ減り、note・scheduleの採用へ移っていた。合計指標だけで退行なしとは判断せず、この候補も未採用とする。二言語補足候補は開発30件では分類26・正解25だったが、再現2表記の片方が未分類のため選ばなかった。

質問文の比較は同じM3・同じ準備済みd1 q8・しきい値0.7で行い、この比較中は入力・製品の質問文・しきい値・保存済み記録を変更していない。0.5/0.6での短文比較も残す。既存の合成30件と22件は再利用した回帰確認であり、新しい実利用のholdoutとは呼ばない。30〜50件の多様な手動正解を集める #2 の条件を、反復した20件で満たした扱いにしない。多様な実メモでの分類品質評価は #2 で継続する。

## 採用基準60%の決定

2026-10-15、ユーザーが「未分類よりは良い」として採用基準を70%から60%へ引き下げ、Issue #1を閉じることを明示した。`Intent.confidenceThreshold` とPRDを0.6へ変更し、60%ちょうどを採用、60%未満は未分類とする。製品の質問文・モデル・日時判定は維持する。

保存済みの20件の確率へ新基準を適用するとtodo19件・未分類1件（note 57.49%が最大）。これは読み取り専用の再判定であり、保存済みラベルが変わった、分類精度が95%になったという意味ではない。新規推論・再分類から新基準を使い、既存DBの一括書換え・自動再処理は行わない。手動修正の保護と多様な手動正解30〜50件による品質評価・既存記録の再処理は #2 で継続する。

同じ製品質問文・準備済みd1で60%/70%を再計算し、既存の著作30件・22件でも比較した。これらは既に使った回帰データで、新たな未見評価ではない。

| 既存合成データ | 70%：分類/正解 | 60%：分類/正解 | 70%→60%の採用ラベル正解率 |
|---|---:|---:|---:|
| 30件 | 24/21 | 26/23 | 87.5% → 88.5% |
| 22件 | 13/13 | 17/17 | 100.0% → 100.0% |

分類数と正解数を分け、未分類を減らす判断を全入力での精度改善と混同しない。[両しきい値・クラス別混同行列](../e2e/results/20261015-mvp-live-acceptance/threshold-adoption.json)（各reportに詳細）。

## 実クライアントと画像ガード

実 `cc-mcp` を現ソースから Release ビルド。音声試験とは別の、著作したサンプル3件だけのDBを使う。

- JSON-RPC initialize / tools/list を往復し、公開ツールが list_inbox / search_captures / get_capture / add_note / mark_done / archive の6つであることを確認。
- clear の get_capture(include_image=true) は画像1枚と受け渡し履歴1件。needs_review は画像0枚・受け渡し履歴0件。これはガード状態からの出力制御の確認で、実OCRやアプリのマスク操作は別に確認する。
- 実 Claude Code に試験セッション限定の MCP 設定を渡し、list_inbox は3件、get_capture は1件、search_captures はkeyword fallbackで1件を取得。権限拒否・JSON-RPCエラーなし。恒久的なMCP設定の変更や個人データの外部送信はしていない。
- ベクトル索引が入った状態の検索、およびアプリ上でマスクした画像の再要求は未完了。索引未投入のDBでmodeだけがvectorになる結果を検索品質の成功には数えない。

試験ハーネスの最初の呼び出しで27文字のIDを指定したためInvalid paramsになり、fixture定義の26文字IDへ修正して全3操作を再実行した。製品の不具合として扱わない。

## 完了判定の範囲

今回のユーザー実機確認と60%基準の採用をもって、ユーザーの明示判断でMVP実装のIssue #1を閉じる。実施した自動検証と実操作の結果を区別し、未確認の手動試験を合格へ変更しない。

- 通常の保存通知の取り消しは手順を案内したが、結果の返信は未受領。録音デバイス中断と画面権限拒否の同時発生、再試行中の取り消し、実アプリのマスク操作後のMCP画像、索引投入済みDBでの実クライアントのベクトルヒットは追加の手動確認として [チェック表](../manual-tests/remaining-acceptance.md) に残す。
- #2 の多様な実データによる意図品質評価・既存記録の再処理、#10 のhelper導入・OS電源policy接続は別の採否・検証項目としてopenを維持する。
- M3での結果を Apple M1 / 16GB での実測や全環境の速度保証とは扱わない。4週間のPRD成功指標は運用評価であり、この20件だけで達成を宣言しない。
